# F410S 仪表盘 MCU (mcuapp.bin) CAN 通讯逆向分析

> 目标文件：`/tmp/dash_work/mcuapp.bin`（210128 字节 = 0x334d0）
> 提取脚本：`/tmp/dash_work/mcuapp_can_extract.py`（`python3 -I` 运行，只读）
> 结论状态：**架构/结构部分为实锤；CAN ID 表为实锤；信号含义未定（需整车 CAN 库交叉验证）**

---

## 0. 一句话核心结论

mcuapp.bin 是一个 **只含「数据」不含「代码」的 MCU OTA 镜像**：它包含向量表、CRC 校验头、约 196KB 的位图/查找表数据、以及一份 **CAN 信号矩阵表**（58 条有效 RAM 地址 ↔ CAN ID 的映射 + 1 条哨兵，CAN ID 0x108~0xF8A）。真正可执行代码（reset 0x34FE8、各中断 handler 0x3D5D4~0x3E064）**不在本文件内**（位于 0x34FE8 之后的独立 flash 区，未被 OTA 包含），所以「CAN 控制器初始化 / 收发代码」无法直接从本文件反汇编——这是本任务最重要的前置发现。

## 1. MCU 架构识别

### 1.1 实测证据（内存映射）

| 证据 | 值 | 含义 |
|---|---|---|
| 初始 SP | `0x10010000` | RAM 位于 `0x10000000`，SP = 顶部 = 恰好 64KB |
| reset handler | `0x00034fe8` | 代码在 flash（base 0x0）的 0x34FE8 |
| IRQ handler 群 | `0x3D5D4 ~ 0x3E064` | 中断向量集中在 0x3D000~0x3E000 |
| 数据区外设地址 | `0x4000xxxx` / `0x4020xxxx` / `0x5000xxxx` | APB/AHB 外设区 |

### 1.2 结论：Cortex-M，最可能是 NXP LPC17xx/LPC40xx 系（或其兼容国产芯）

- **RAM@0x10000000 + flash@0x0 + 外设 0x40000000(APB)/0x50000000(AHB)** 这套内存映射是 NXP LPC17xx/40xx（Cortex-M3/M4）的典型特征。
- **SP = 0x10010000 = 64KB 整**，与 **LPC1768**（512KB flash + 64KB SRAM + 双 CAN）严丝合缝。LPC1768 是国产车机/仪表多年主流主控。
- 向量表是「SP 指针 + handler 地址指针」格式，即 Cortex-M 风格（ARM7/9 用的是跳转指令向量，不是指针表）。

### 1.3 一个必须说明的「异常」：handler 地址全是偶数（bit0=0）

实测向量表 8 个 u32：`[0x10010000, 0x34fe8, 0x3d5d4, 0x3d5d8, 0x0, 0x3d5dc, 0x0, 0xeff02e90]`。
reset = `0x34fe8`，其它 handler `0x3d5d4/0x3d5d8/...` **全部为偶数**，不是标准 Cortex-M 向量表的「Thumb 地址（bit0=1）」。

两种解释（**均无法从本文件定论，因为代码缺失**）：

1. **仍是 Cortex-M**：ARMv7-M 在异常进入时会强制 Thumb 态、忽略向量 LSB，因此偶数地址在真实 Cortex-M 硬件上照常运行——只是工具链/启动文件没写 bit0（某些国产 SDK 的常见现象）。内存映射强烈支持这一条。
2. **ARM 老核（ARM7/ARM9/Cortex-R）跑 ARM 态**：偶数地址天然合法。但 ARM7/9 的向量表应是跳转指令而非指针表，且 ARM7（LPC2xxx）SRAM 在 0x40000000 而非 0x10000000，与本文件不符。

**倾向结论：Cortex-M（LPC17xx/40xx 系或兼容芯），偶数向量地址是工具链/启动文件未置 Thumb 位所致。** 需要拿到 0x34FE8 之后的代码段才能 100% 坐实。

### 1.4 数据区中观测到的外设地址（实测，但无法映射到具体外设——代码缺失）

`0x40001580`(x22)、`0x40200000`(x18)、`0x50000180`(x15)、`0x40002880`(x13)、`0x50000000`(x11)、`0x50000080`(x10)、`0x40000100`、`0x40001c00`、`0x40000a80`、`0x40001280`、`0x50000100`、`0x40000980`、`0x40001600`、`0x40000580`、`0x4000000c`、`0x40002f80`、`0x402000a0`、`0x500000c0`、`0x50000140` 等。

- **未找到**任何常见 CAN 控制器基址：`0x40044000/0x40048000`(LPC17xx CAN1/2)、`0x4003C000`(LPC CAN AF)、`0x40006400/0x40006800`(STM32 bxCAN)、`0x40024000`(S32K FlexCAN)、`0x40050000`(LPC11C C_CAN) —— 全部 NOT FOUND。
- 原因：引用这些寄存器地址的**代码不在本文件**，数据区里这些值是给代码用的常量。
- `0x40001580 / 0x40200000 / 0x50000180` 常与 `0xffff / 0xffff0000` 成对出现（见 0x32570/0x32620/0x32700），形态像 **flash 烧写/外设写序列** 而非 CAN 寄存器。

> **CAN 控制器基址：未确定（待验证）。** 推测 0x4000xxxx 群中的某一组是 CAN，但需要代码段实锤。

| 0x0000~0x0200 | 向量表（front，SP=0x10010000，handler 群 0x3D5D4~0x3E064） |

| 0x0210~0x025f | 设备信息串（"8450555"、型号 "410S00600HA0140002F410S--SBH--26154258"） |

| 0x332c0~0x334d0 | 尾部 2 个调度描述符 |

### 2.1 头部 CRC 校验链（新发现，实锤）

- 头部字段 `0x204 = 0x1c677137` **= `zlib.crc32(data[0x210:])`**（标准 reflected CRC32，带 final XOR，覆盖 0x210 到文件尾）。
- `0x200 = 0x332c0` = payload 长度（`0x210 + 0x332c0 = 0x334d0` = 文件尾，精确吻合）。
- 即文件 = 向量表(0x200) + 头(0x10) + payload(0x332c0)，**自洽完整、未截断**。
- 注意：这里用的是 **zlib 标准 CRC32**，与之前笔记里 update.bin/ROMA/BANI 用的「normal CRC32 无 final XOR」不同（mcuapp 是另一条校验）。

### 2.2 「back 区」第二张向量表（实测）

`0x30914` 处：SP=`0x10010000`、reset=`0x34fe8`、其余 handler 全部 = `0x10001e98`（RAM 地址），另有零星 `0x10001d14/0x10001d48/0x10001d70/0x10001d8c/0x10001d90/0x10001dfc/0x10001e94`。
- 与笔记中「back@0x30914」一致，但 **back 区 handler 指向 RAM**，更像 RAM 驻留引导/升级程序（或 A/B 区第二镜像的向量表）。
- front 与 back 的 reset **都是 0x34fe8** —— 两个区共用同一段固定代码入口。

## 3. CAN 信号矩阵（核心交付）

### 3.1 信号表（实测，@0x30450，16 字节/条，58 条有效 + 1 条哨兵）

结构：`{u32 f0, u32 RAM地址, u32 CAN_ID, u32 f3}`，RAM 地址均在 `0x10000000` 区。

> ⚠️ **条数说明**：表区域 0x30450~0x30800 共 944 字节 = 59×16B，但第 59 条（index #58，CAN_ID=0x40000D00、RAM=0x40000D80）非有效 11-bit 标准 ID（< 0x800），是哨兵/padding 条目。实际有效信号映射 = **58 条**。

**前 9 条（特殊，f0/f3 各异）**：

| CAN ID | RAM 地址 | f0 | f3 |
|---|---|---|---|
| 0x108 | 0x10000648 | 4 | 1 |
| 0x110 | 0x1000064c | 4 | 1 |
| 0x118 | 0x10000650 | 4 | 9 |
| 0x130 | 0x10000654 | 0xC | 0x20 |
| 0x176 | 0x10000660 | 0x23 | 0x11 |
| 0x19E | 0x10000680 | 0x14 | 4 |
| 0x1AC | 0x10000694 | 7 | 4 |
| 0x1BA | 0x10000698 | 7 | 1 |
| 0x1C2 | 0x1000069C | 4 | 0x21 |

**后 49 条（规则块，f0=0x24、f3=0x21 恒定，CAN ID 步进 0x48，RAM 步进 0x24）**：

CAN ID 序列：`0x20A, 0x252, 0x29A, 0x2E2, 0x32A, 0x372, 0x3BA, 0x402, 0x44A, 0x492, 0x4DA, 0x522, 0x56A, 0x5B2, 0x5FA, 0x642, 0x68A, 0x6D2, 0x71A, 0x762, 0x7AA, 0x7F2, 0x83A, 0x882, 0x8CA, 0x912, 0x95A, 0x9A2, 0x9EA, 0xA32, 0xA7A, 0xAC2, 0xB0A, 0xB52, 0xB9A, 0xBE2, 0xC2A, 0xC72, 0xCBA, 0xD02, 0xD4A, 0xD92, 0xDDA, 0xE22, 0xE6A, 0xEB2, 0xEFA, 0xF42, 0xF8A`
对应 RAM：`0x100006A0` 起，每 +0x24(36) 一条，至 `0x10000D84`。

> 全部为 11-bit 标准 CAN ID（< 0x800）。**这是「RAM 变量 ↔ CAN ID」的信号映射表**，是最实锤的 CAN 通讯证据。

### 3.2 扩展 ID 表（实测，@0x30328，24-bit，25 条）

`0x080119, 0x08011A, 0x08011B, ..., 0x080131`（低字节 0x19→0x31 递增）。
- 形态上是 29-bit 扩展 CAN ID 或 `{index, 0x01, 0x08}` 三字节记录。**用途未定（推断：诊断/扩展帧 ID 集合）**。
- 紧随其后的交错表（@0x30370）成对出现 `0x0401xx ↔ 0x0402yy`（yy 为 0x33,0x35,...0x63 奇数递增）、`0x0201xx ↔ 0x0204yy`（yy 为 0x65,0x67,...），是一张 **id→id 映射表**，具体语义未定。

### 3.3 报文周期 / 调度（实测，@0x332c0、0x33320）

两个描述符，各带 6 个数据块指针 + 4 个时间参数：

```
0x332c0: {0xfff, 2, ptrs=[0x2cd38,0x2d130,0x2d35e,0x2d18c,0x2d270,0x2d354], T=25, 500, 2000, 1000}
0x33320: {5, 0,    ptrs=[0x2cd78,0x2d130,0x2d35e,0x2d18c,0x2d270,0x2d354], T=30, 500, 2000, 1000}
```

- 时间参数 **25/30ms、500ms、1000ms、2000ms** —— 典型的 CAN 报文发送周期（快帧 25~30ms、中帧 500ms、慢帧 1~2s）。
- 指针指向数据区内的 6 个数据块（`0x2cd38/0x2d130/...`，非 4 字节对齐 ⇒ 是数据偏移不是函数指针）。

### 3.4 掩码/映射表（实测，@0x2fba0 起）

表首出现：`0x0FFFFF`、`0x7FF`（= 11-bit 标准 ID 掩码）、`0x380/0x39E/0x37E/0x35E`（具体 CAN ID）、`0x7FFFF`（19-bit 掩码），随后是 0~0x64 的**重排序列**（信号读/送顺序表）。

## 4. 反汇编方法与关键地址

- **方法**：capstone 5.0.7（已装）。对 dense 区（0x260~0x2fb00）分别用 `CS_MODE_ARM` 与 `CS_MODE_THUMB` 反汇编，均得到无意义指令（重复的 `stm r0!`、`movs r5,#n` 等）⇒ 该区是数据非代码。
- **判定代码缺失的依据**：
  1. 向量表 reset=0x34fe8、handler 0x3D5D4~0x3E064 全部 > 文件尾 0x334d0。
  2. 文件内函数指针表（@0x2d130）指向 `0x372c4/0x37390/0x375b8/0x36694/...`（均 > 文件尾）。
  3. 全文件扫描 `STMFD(0xE92D)/LDMFD(0xE8BD)/B(0xEA)/BL(0xEB)/PUSH(0xB5)/POP(0xBD)` 四种 prologue opcode，**命中数均为 0**。
- **关键地址速查**：
  - 向量表 front：0x0000；back：0x30914
  - 头部 + CRC：0x200~0x20c
  - CAN 信号表：0x30450（58 条有效 + 1 哨兵）
  - 扩展 ID 表：0x30328；映射表：0x30370
  - 掩码/排列表：0x2fba0；周期表：0x2fcd0
  - 函数指针表：0x2d130；调度描述符：0x332c0、0x33320
  - 字符串："F410S 8.8 INCH EV/PHEV"@0x14d1c/0x14d30、"GDC Is Burning"@0x2e188、"IO IS LOCK !!!"@0x2e170、"%02X%02X.%02X.%02X"@0x14cf0
